A teaching guide to the finalized Basys 3 project. Written for someone who did not write the code and wants to
understand it well enough to design another FPGA game.
Design snapshot: 14 October 2026, xc7a35tcpg236-1, Vivado 2025.2. Simultaneous 96 x 64 color OLED on JC and
native 800 x 600 VGA. One/two-ball selection is in the menu; SW1 is ignored. The optional mouse uses SW0. The
authoritative implementation evidence is build/manifest.json and docs/VALIDATION.md.
This document explains the actual RTL, then turns its design choices into reusable lessons. Small teaching snippets are
marked as examples; they are not replacements for the complete modules. A section called "rebuild" describes a new
implementation you can develop yourself, rather than instructions to paste this entire project into a new folder.
1. How to read and use this guide
Start with the architecture and digital-design foundations before reading the arithmetic-heavy collision code. Then follow
one action through the design: press Center, charge, release, move a ball, collide, score, and draw the next frame. That
path reveals why the modules exist and which signals connect them.
On a second pass, open each named source file beside its explanation. All custom RTL lives in
FDP2026.srcs/sources_1/new/. The top file contains three modules, so "eleven custom RTL files" means thirteen custom
modules. The supplied Verilog OLED interface and two VHDL mouse files add three more modules. They are preserved
byte-for-byte.
Use three levels of understanding. First, know what each module promises at its ports. Second, know when its registers
change. Third, know how the combinational logic computes the next value. Understanding only the pictures or only the
equations is insufficient: a correct FPGA system needs the right values on the right clock edges.
After each major topic, explain it aloud without referring to the source. For example: why does one button press create
one menu event, while a held button continuously operates a flipper? Why do two balls share a collision circuit? Why
does a graphics frame contain a copy of the game state? These questions test the design principles you will need in a
new project.
The original proposal separates motion, collisions, graphics, and game/input. The final design follows that decomposition
and adds OLED output, moving objects, two-ball play, reduced scoring, richer feedback, and original reaction graphics.
Scheduling and member-allocation text in the proposal are historical context, not descriptions of a different current
circuit.
2. What the complete machine does
This project implements a pinball game as interconnected digital circuits. It does not run a C game loop on a processor.
The FPGA stores positions, velocities, game state, score, timers and input history in registers. Arithmetic and
comparison circuits continuously calculate candidate results. Clock edges decide when those candidates become the
new state.
The table has three bumpers, two side targets, three pass-through rollover lanes, a spinner, two diamond slings, three
stand-up targets, walls, guides, a shooter lane, and two flippers. Two bumpers move on short tracks. A game has three
lives, with finite launch/target saves; the turn continues until all selected balls drain. Both displays show the same game,
although they do not necessarily start their frames at the same instant.
Board controls cover all essential actions. The mouse is an additional input device. The VGA connector carries RGB and
synchronization signals; an external active VGA-to-HDMI converter produces HDMI. The FPGA does not generate a
native HDMI/TMDS signal in this project.

4. Digital-design foundations before reading the source
Combinational logic versus stored state
A combinational circuit produces an output from its current inputs without remembering previous values. An assign
expression, comparison or fully assigned always @* block can describe such logic. In a renderer, the pixel at (x,y) is
determined from the coordinates and the selected scene. No sequence of software drawing calls is required.
A clocked always @(posedge clk) block describes state updated at clock edges. position_x, score_bcd, state,
debounce counts and timers are examples of remembered values. A reg declaration by itself does not guarantee a
physical flip-flop: the assignment context determines whether synthesis infers combinational logic, a flip-flop, or
accidentally a latch.
Teaching example, not a drop-in project module:
// Combinational condition: a rectangle exists at these coordinates.
wire inside_box = x >= 10 && x < 20 && y >= 8 && y < 16;
// Sequential state: move only on a selected update edge.
always @(posedge clk) begin
    if (reset)
        object_x <= 7'd10;
    else if (step_enable)
        object_x <= object_x + 1'b1;
end
All module instances operate concurrently. A source file's ordering does not mean the FPGA finishes input processing,
then runs rules, then runs graphics as separate software tasks. Nevertheless, register boundaries introduce cycle
latency. One module may consume a command on the following clock because nonblocking assignments publish it after
the current edge.
Why assignment type matters
Clocked state in this project uses nonblocking assignments, <=. The right-hand sides use values from before the edge,
and the left-hand sides update together. Combinational calculation uses blocking assignments, =, so a later expression
in the block can use a temporary result computed earlier in that block.
Consider this teaching example:
always @(posedge clk) begin
    a <= b;
    c <= a;
end
After an edge, a holds the old b, while c holds the old a. This is a two-register pipeline; c does not immediately receive
the new b. The game's award pipeline and delayed mouse-event handling depend on this distinction.
Within one clocked block, multiple active nonblocking assignments to the same register are resolved by their procedural
order: the last executed assignment wins. The game intentionally puts reset/new-game/drain and collection updates in
particular places. Reordering code for appearance can change a simultaneous-event outcome.
In a combinational block, give every result a default before conditional overrides. If some path fails to assign a result, the
result must retain its previous value, so synthesis may infer a latch. A latch can be useful in a deliberate design, but
these custom combinational modules do not intend to infer one.
Width, signedness and safe arithmetic
Hardware numbers have finite widths. Seven unsigned bits represent 0 through 127. Six unsigned bits represent 0
through 63. Sixteen signed bits represent -32,768 through 32,767. Truncating, adding or shifting a number can change
its meaning if the result width is too small or an operand unexpectedly becomes unsigned.

Use explicit widths where the design depends on a range: 3'd2 for a state, 16'sd256 for a signed Q8 unit, and a wider
sum when carry is possible. A concatenation such as {1'b0,value} is unsigned unless deliberately cast; $signed(...)
appears around appropriate physics operands for this reason.
The debouncer illustrates why parameterization must include width. Its count has to reach STABLE_CYCLES-1. With
STABLE_CYCLES=1048577 (1,048,577 samples), the terminal value is 1,048,576. A fixed 20-bit counter cannot reach it, so
the long-interval version never accepted a stable press. The final code uses $clog2(STABLE_CYCLES), with a minimum of
one bit, to size the counter for the positive configured interval.
Custom source files use default_nettype none and explicit net ports. This turns a misspelled signal into a compilation
failure instead of silently creating a one-bit wire. The directive is restored to wire at each file's end so it does not impose
new requirements on the supplied modules. It is a maintenance safeguard; it does not improve gameplay by itself.

Follow a normal launch. The game is READY and observes a held launch control. Every fourth tick changes charge.
When the control is released, rules assert launch, enter PLAY, and establish eligible launch protection. On the next
main-clock edge physics consumes the command and assigns launch velocities. At a later physics tick it snapshots
operands, computes contacts, and commits corrected state after its isolated calculation window. Hits then become score
transactions and effects. A display next captures a producer bundle at its frame boundary and paints that state for the full
frame.
Every arrow in this description has a contract. If a new module expects a held level but you send a one-cycle pulse, it
may operate for just 10 ns. If it expects a pulse but you send a held level, it may repeat hundreds of millions of times.
Write down the meaning, clock domain, units, validity and lifetime of each signal before wiring modules together.
6. Clocks, resets, physical inputs and the mouse
Three real clocks and one slow enable
The board supplies 100 MHz. The top's four-bit divider has a bit that toggles at 100 MHz / 16 = 6.25 MHz; a BUFG
routes that OLED clock globally. An MMCM multiplies the main clock by 10 to a 1 GHz VCO, then divides by 25 to
produce 40 MHz for VGA. Dedicated clock resources distribute actual clocks with controlled skew.
The physics counter reaches PHYSICS_TICK_LAST = 416665 and resets. Counting from zero includes 416,666 main-clock
edges per pulse. Thus the actual rate is 100000000 / 416666 = 240.000384... Hz, conventionally described as 240 Hz.
Most game counters act on tick while their registers remain clocked by 100 MHz.
Teaching example:
// Preferred pattern for a slower operation in the existing clock domain.
always @(posedge clk) begin
    if (reset)
        timer <= 0;
    else if (tick && timer != 0)
        timer <= timer - 1'b1;
end

Using always @(posedge tick) would turn an enable pulse into another clock domain. It would require different clock
routing, reset treatment and timing constraints. The clock-enable pattern keeps short-lived actions, rule pipelines and the
collision scheduler in one main domain.
Reset is part of the design, not just a testbench convenience
The top initializes a 32-bit all-ones shift register and shifts zeros through it after configuration. Its nonzero value keeps
system reset asserted at startup. Switches pass through two synchronizer registers; synchronized SW15 also asserts
reset. Reset clears score and high score, menu selection, commands, physics, effects and mouse configuration.
The VGA clock generator has a lock indication. If lock disappears, the VGA reset pipeline asserts asynchronously; after
lock, the pipeline releases reset through pixel-clock edges. This allows video logic to restart coherently even when the
pixel clock was temporarily unavailable. Do not treat an unlocked generated clock as a valid display clock.
Synchronization, debounce and edge detection are different
A physical button can change near a clock edge and can bounce mechanically. Two synchronization registers reduce
the chance that metastability propagates into game logic. They do not by themselves eliminate bounce. Each input's
debounce count advances only while the synchronized sample disagrees with the accepted level. When the count
reaches its configured terminal value, the accepted level changes once.
At 100 MHz, 500,000 samples correspond to 5 ms. The five channels have independent counters, so bounce on one
button cannot delay another. down is a held level; pressed is a one-cycle rising event. Left/right flippers use held controls,
while menu toggles and pause use events. A held U therefore toggles the ball mode once, not continuously.
The mouse is a supplied interface plus a game adapter
The Basys 3's USB-A host connection is bridged to PS/2-style signals for the FPGA. The protected MouseCtl and
Ps2Interface handle protocol communication. The game supplies four initial configuration requests: maximum X 95,
maximum Y 63, initial X 48 and initial Y 32. They use logical OLED coordinates, so one control layout can serve both
displays.
Mouse buttons and coordinates can update during different parts of a packet. The top delays new_event and stores
previous complete-packet buttons and cursor coordinates. Held flipper/launch controls use those committed button
levels. On the dispatch cycle, click hit-testing uses the final packet coordinates, avoiding a click based on the previous Y
position.
Click detection compares the current complete-packet left button with the previous committed left button. SW0 gates
mouse actions. The clickable rectangles are deliberately bounded: mode, difficulty, Start, Resume and Restart. A
decorative title or empty margin is not an action. The mouse cursor and hover graphics use the same logical layout;
different-looking buttons must still have matching control regions.
Board and mouse controls are combined with OR conditions for held actions. Changing input devices therefore does not
require another physics engine. Nudge is a separate edge action, rejected in the shooter lane and limited by a 480-tick
cooldown. A similar adapter pattern works for a joystick, keypad or another peripheral: translate its protocol into the
game's existing held and event signals.
7. From controls to game rules
The module pinball_game answers questions such as "is the game running?", "does this drain cost a life?", and "what
score should this contact earn?". It does not calculate ball trajectories or produce display pixels. That separation is the
first design idea to keep when rebuilding the project: the rules consume events from the physics datapath and publish
state for the displays. My_Top_Module connects these modules and translates physical inputs into commands.
Every game register uses the 100 MHz clk. The slower tick is a one-clock enable, not a separate game clock.

active is the combinational expression state == PLAY. Physics uses this enable to decide whether it may begin another
update. prepare and launch are one-clock command pulses: the clocked block clears them by default, then asserts the
appropriate one when a transition needs it. Preparing resets ball placement; launching consumes the current charge. An
illegal state falls back to MENU, while OVER stays OVER until a higher-priority command changes it.
The explicit transition order is reset first, then menu_press, then new_game, then an accepted drained event, then ordinary
state-specific commands. This order is part of the specification. If D, U and drain arrive together, returning to MENU
wins. If the last unprotected life drains on the same edge as U, OVER wins. For a non-final or saved drain,
next_life_paused preserves the simultaneous pause/resume request and records READY as the state to resume into.
Pause needs special care because physics takes several clocks to finish an update. Setting active=0 prevents another
update but cannot erase one already calculating. accepts_play_event therefore remains true in PAUSE when
resume_state==PLAY. That final hit or drain is still processed, including its save entitlement and award. A pause from
READY does not accept gameplay results. The score pipeline also finishes already accepted transactions during pause
or drain. This distinction between stopping new work and finishing outstanding work is useful in any FSM controlling a
multicycle datapath.
Counters are not all governed by the same condition. anim, hit flashes and feature_timer advance on tick in every
state except PAUSE. Combo, gold-target and spinner timers advance only in PLAY. The pseudorandom rng continues
on system clocks even while paused. Thus "paused" means frozen gameplay, not that every flip-flop in the device stops
changing.
9. Charge, lives and protected relaunches
charge is a six-bit value, 0 through 63. In READY, holding launch_down sets charging. A two-bit charge_div permits one
power step per four ticks: approximately 60 steps per second. charge_falling selects whether the next step increases
or decreases power. The sequence is 0,1,...,62,63,62,...,1,0,1,...; direction reverses on arrival, with no extra
endpoint hold. Each half-cycle takes approximately 1.05 seconds. Releasing after a charge asserts launch, changes the
state to PLAY, and clamps a power below 16 up to 16 so a brief tap can leave the lane.
The first C press starts the game; continuing to hold C in READY begins charging. A READY pause freezes the current
spring level, but resuming clears charging, charge, charge_div and direction. This prevents a release during pause from
unexpectedly launching old stored power. The player can charge again after resuming.
lives counts remaining turns, including the current one. A new game sets it to three. An unprotected drain changes
three to two, then two to one; draining with one remaining sets zero and OVER. A "turn" can contain a pair of balls.
pinball_physics reports drained to the game only when the final surviving partner drains, so losing the first ball in
two-ball mode does not deduct a life or prepare another shot. Both balls are prepared and launched together for the next
turn.

Protection deliberately allows more than three shots. On a fresh-life launch, launch_save_eligible loads
save_timer=720, approximately three seconds. The timer decreases only during PLAY and when in_lane is false. In
two-ball mode, in_lane remains true only while every surviving ball is in its lane, so the countdown begins when either
survivor enters the table. Completing both side targets grants save_timer=1440, approximately six seconds.
If the final drain occurs while save_timer!=0, or on the same edge as target_complete, the game prepares another shot
without reducing lives. It consumes protection by clearing the timer and setting launch_save_eligible=0. That saved
relaunch receives no automatic three-second save. A later unprotected life loss makes the next life eligible again. The
protection is shared by the turn; it is not a separate timer for each ball. The renderers use the same published
save_timer to make protected balls and their trail bright blue.
10. Contact masks, combos and collection rewards
hit_events is a 14-bit event mask. Each bit identifies a scoring contact, not a persistent overlap. Physics filters raw
collision contacts with per-ball arming masks, so one ball resting near a bumper cannot earn points every tick. In two-ball
mode the two results are emitted as separate transactions, allowing both contacts to score.

11. Half-point scoring and the three-edge pipeline
Four seven-segment digits can represent 0000-9999. score_bcd and high_bcd therefore hold four binary-coded decimal
nibbles: 16'h0123 represents decimal 123. It is not the binary integer 16'd123. The carry function add_bcd adds each digit
and propagates a decimal carry; a carry beyond the thousands digit saturates the result at 16'h9999. Valid BCD values
also compare in numeric order, so the independent score_bcd > high_bcd comparison is safe.
Scoring is pipelined to avoid placing combo arithmetic, conversion and four-digit carry on one 100 MHz path. Stage 1
accepts the event and registers award_units_1. Stage 2 adds the stored score_half, converts the whole part to
award_bcd_2, and preserves the low bit as the new fractional remainder. Stage 3 commits the BCD addition and updates
last_award_bcd. Valid flags award_valid_1 and award_valid_2 distinguish a real zero-point fractional credit from no
transaction.
Consider starting with score and high score both 0098, half remainder 0, and expired combo. Two consecutive
bumper-contact transactions earn 1 unit at ×1 and 2 units at ×2. No collection or gold bonus applies:

The earned total is 1.5 points, with 0.5 retained for a future transaction. Conversion happens in transaction order, so
adjacent awards cannot lose that remainder. The largest synthetic transaction, all 14 contacts at ×4 plus every
applicable flat bonus, is 110 units or 55 points. That bound justifies seven-bit award registers and a small
compare/subtract decimal converter instead of a general divider. At saturation, last_award_bcd still describes the
transaction's whole credit rather than the smaller increase visible in the capped score.
Reset clears both scores. A new game clears the current score, fractional carry and pipeline valid bits but preserves the
session high score. Returning to MENU also preserves the high score. A drain resets combo but preserves accumulated
score and collection progress; those collections reset on completion or a new game.
12. Sequential reasoning and a rebuilding exercise
In always @(posedge clk), nonblocking assignments read the pre-edge values and schedule new register values. This
explains why E1 uses A while also accepting B, and why high score trails a committed score by one clock. It also
explains timer tests such as if(combo_timer==1): the condition sees the old one while decrement schedules zero. Later
assignments to the same register in this block win, intentionally allowing a fresh hit to reload a timer after the generic
countdown would decrement it.
For a small rebuild, first implement MENU, READY, PLAY and OVER with one ball, a held spring control and one
bumper event. Add PAUSE and a remembered resume state next. Only after those transitions work should you add a
decimal score and staged awards. This progression exercises the EE2026 concepts of combinational next-value logic,
sequential registers, FSM control, counter enables, bit masks, numeric encoding and controller/datapath interfaces.
An illustrative pattern, not a drop-in replacement, is:

13. Motion is a sampled calculation, not a moving pixel
Read pinball_physics.v for the stored world state and scheduling, then pinball_collision.v for the combinational
contact calculation. The physics module stores position, velocity, shooter-lane status and visibility separately for each
ball. It also owns the moving bumper centres and flipper angles. The collision module receives a snapshot of these
quantities and returns corrected position, corrected velocity and a 14-bit contact mask. Scoring belongs to
pinball_game.v; collision detection does not directly add points.
The board clock is 100 MHz, but the world advances on a 240 Hz enable named tick. One world step therefore
represents approximately 4.167 ms. Registers remain clocked at 100 MHz; the enable decides when a new physical step
may begin. This distinction connects directly to synchronous digital design: a slowly changing game can use a fast clock
without inventing another clock domain.
The logical table uses OLED-sized coordinates: x increases to the right and y increases downwards. Consequently
positive vertical velocity means falling, negative vertical velocity means rising, and gravity is positive. A ball is more than
its displayed integer coordinate. Between x=20 and x=21 there are 256 representable fractional positions.

14. Contacts: approximating useful geometry in hardware
pinball_collision.v is an always @* combinational block. It initializes every output and temporary, then applies contact
tests in a stable priority order. A solid_contact flag allows one main solid-object response per step: bumpers, stand-up
targets, slings, side targets, flippers and guides are considered in order. Outer boundary correction still follows. Sensor
regions such as rollovers and the spinner report passage without stopping the ball.

This ordered approximation is intentional. The project is an arcade model, not a general rigid-body solver. It has no
ball-to-ball collision, spin, continuous contact manifold or general search for the earliest collision among all objects. Two
balls may pass through each other. This keeps the hardware cost and behavior predictable.
Inflated objects and simple distance tests
Rather than calculate a circle intersecting another shape, enlarge the object by the ball radius and treat the ball centre as
a point. The drawn bumper radius is three logical pixels and the ball radius is one. Its clearance envelope is an octagon
described by:
abs(dx) <= 1024              // 4 pixels
abs(dy) <= 1024              // 4 pixels
abs(dx) + abs(dy) <= 1472    // 5.75 pixels
Here dx and dy are ball position minus bumper centre in Q8 units. These comparisons use absolute values, adders and
comparators instead of square roots. The response chooses an axis or 45-degree normal, providing eight useful
rebound directions without trigonometric hardware.
The three permanent stand-ups at (34,20), (42,20) and (50,20) use a square clearance of ±2 pixels around their centres.
Slings at (17,41) and (69,41) use a diamond: abs(dx)+abs(dy)<=1024, a Manhattan radius of four pixels. These shapes
match the inexpensive drawn forms well enough for play.
Why checking the final position is insufficient
A ball can graze a corner between two samples even though both endpoints are outside the clearance shape. This is
called tunnelling. The code therefore also tests the segment from the previous ball position to its proposed position.
swept_octagon considers the four pairs of octagon faces. Each face has a projection coordinate perpendicular to it and a
tangent coordinate along it. For a vertical face these are x and y; for a diagonal face they are x+y and x-y. Reflecting
negative projection values lets one formula describe either sign of a face.
Suppose the old projection P0 is outside boundary B, and the new projection P1 crosses inward. The crossing fraction
would be:
D = P0 - P1        // positive denominator
N = P0 - B
t = N/D
crossing_tangent = T0 + (T1-T0)*N/D
Crossing the infinite line is insufficient: the crossing must fall on the finite face. If its tangent extent is ±L, division can be
removed:
I = T0*D + (T1-T0)*N
-L*D <= I <= L*D
This is what the signed wide intercept and tangent_bound calculations implement. For example, with B=1024, L=448,
P0=1100, P1=900, T0=300 and T1=500, D=200, N=76 and I=75200. Because L*D=89600, the crossing lies on the face:
its mathematical tangent is 376. With T0=500 and T1=700 instead, the crossing tangent becomes 576, beyond 448, and
the segment is a near miss. A collision detector that only asks whether the line was crossed would falsely bounce the
second trajectory.
Stand-ups reuse swept_clearance for rectangular clearance. The bounded step sizes allow it to select the old outside
face instead of building every face calculation separately. The sling diamond becomes a rectangle in transformed
coordinates u=x+y, v=x-y, so the same function handles its swept corners. The 17-, 18- and 36-bit intermediates matter:
products can overflow even when each coordinate fits in 16 bits. Width selection is a direct application of finite-width
arithmetic taught in digital design.

Correct penetration, reflect only inward motion
Detection is followed by two separate actions: move an overlapping ball outside the object, and change velocity only if it
approaches the surface. Otherwise an already departing ball can be reflected back into the object every step and appear
stuck.
For a right-facing bumper surface, positive x is outward. A relative x velocity below zero approaches the surface, so it
reflects; positive x is already leaving. For a diagonal, the approach expression adds the signed components along the
selected normal. The approach<0 test also gates the hit event. Axis bumper rebounds retain roughly 7/8 of incoming
speed, add a small impulse of 24 Q8 units, and enforce a useful minimum of 160. Diagonal rebounds swap/sign-change
the two components, then add a 32-unit outward impulse. These impulses deliberately make a pinball bumper energized
rather than a passive wall.
Moving bumpers require relative velocity. If the bumper itself has velocity c, reflect ball_velocity-c, then add c back.
Old and new relative positions also subtract the matching old and new bumper centres. Mixing an old ball position with a
new bumper centre would distort the swept segment and create false hits.
The left bumper moves vertically at x=26, y=22..28; the right moves horizontally at y=22, x=58..66. Each accepted world
step moves a centre by four Q8 units, or 4*240/256 = 3.75 pixels/s. End comparisons reverse direction. Both ball
calculations see one shared old/next pair, and the centres commit once after the complete world step. Do not advance
the world once per ball: that would make two-ball mode move bumpers twice as fast.
Flippers are controlled surfaces with different responses
Each flipper has angle states 0..4. Holding the button advances one angle per accepted physics tick; releasing retreats
one. Four transitions take about 16.7 ms. The left pivot is (21,53), the right (65,53), and each reaches 18 pixels toward
the middle. A lookup function gives inner-tip offsets +5,+3,+1,-2,-4, approximating rotation without sine/cosine.
The surface height is 53*256 + local_x*tip_offset/18. The previous ball height is checked as well as the proposed
height. A ball travelling below a flipper should continue below it, rather than being teleported onto its top. A rising flipper
may sweep into a nearby ball within its clearance band.
A rising flipper gives a strong upward and inward impulse that grows toward the tip. A held raised flipper gives a weaker
return. A released flipper halves sufficiently fast downward speed, while a low-energy ball rolls toward its tip instead of
receiving an endless upward impulse. Post-collision speed limits still apply. Side guides join the visible pivots; matching
rendered geometry and collision endpoints prevents invisible rails.

 Shared two-ball calculation timeline

The expensive combinational collision block exists once. Physics chooses a ball's operands, snapshots them into
collision_* registers, waits for the calculation, and stores its result. This is resource sharing controlled by a small
sequential scheduler, not two concurrent software function calls.
At 100 MHz one clock is 10 ns. A collision transaction gets 16 clocks, or 160 ns. One-ball mode commits after that
window. With both balls launched, the first result goes into stage_* registers while the displayed/live ball positions
remain unchanged. A separate handover clock selects and captures ball 2's operands, followed by its 16-clock window:
edge 0     capture ball 1 and the world's old/next bumper centres
edge 16    stage ball 1 result; select second-ball work
edge 17    capture ball 2 operands
edge 33    commit both ball results and the moving centres together
The pair costs 330 ns, negligible against the 4.167 ms physics period. Atomic final position commits prevent a renderer
or effects module observing a newly moved ball 1 alongside an old ball 2. If only one survives, it returns to the 16-clock
path; losing one ball does not immediately end the round.
Both balls can hit the same object in one step. OR-ing their contact masks would count that as only one contact. At the
pair commit, the first mask appears with hit_ball=0; the second appears four system clocks later with hit_ball=1. If
both balls drained, the final drained pulse appears six clocks after commit. Registered outputs are consumed by the
game module on the following clock edge, so the relative sequence remains first contact, second contact, final drain.
This preserves both awards before the game leaves PLAY. The four-clock spacing also leaves time for combo/progress
changes from the first contact to influence the second transaction.
Each ball has separate hit_armed bits and 14 cooldown counters. A scored contact disarms its bit and starts a 16-step
cooldown, about 66.7 ms. Time expiry alone does not rearm it: the ball must also leave a larger object-specific envelope.
This hysteresis prevents repeated points while resting against a bumper or sitting inside a sensor. The other ball retains
independent eligibility.
A one-clock nudge may arrive between physics ticks, so nudge_pending holds it. The accepted batch captures it once for
both calculations; a late nudge waits for the next batch. Each eligible ball receives ±48 horizontally toward the middle,
and -80 vertically, subject to limits. In-lane balls receive no nudge. This avoids the bug where a late control pulse affects
only ball 2.
Pause prevents accepting another world step. An already accepted transaction finishes normally, including deferred
contact/drain outputs; the rules module explicitly accepts that final event while paused. Reset or prepare instead cancels
the calculation, staging and pending event timers. Preparation is used for a new round/menu, so stale contacts cannot
arrive in the newly prepared game.
The timing constraint is a promise made by the RTL
Pinball_Physics_Timing.xdc applies a 16-cycle setup exception and a matching 15-cycle hold exception from isolated
collision snapshots to specified result-state registers. Ordinary control paths still have a 10 ns requirement. The
calculation is not required to settle in one clock because its operands remain unchanged and its result is not captured
until 16 clocks later.
This is legal only because the scheduler actually enforces that contract. Declaring a slow path multicycle does not make
unsafe hardware correct. Changing snapshots midway, committing early, or broadly applying the exception to controls
would invalidate it. The paired hold adjustment prevents the setup exception from also imposing an unintended later hold
requirement. The build checks that the expected snapshot registers exist; timing reports must still be inspected after
implementation.

16. Recreate the physics incrementally
Begin with one signed Q8 position/velocity pair and a tick enable. Simulate free flight against the worked example before
adding graphics. Add speed clamps and axis walls, separating penetration correction from inward-only reflection. Then
implement one stationary bumper and test it from every side. Add flippers and a drain; ensure a released flipper cannot
sustain the ball forever. Only after this works add sensors, scoring pulses, moving-object relative coordinates and swept
corners. Finally share the engine with a second set of registers and add atomic commit/event scheduling. This order
makes each failure attributable to a small new idea.
Useful exercises have measurable outcomes:
- Send a ball away from an overlapping wall: its position corrects, but velocity does not reverse inward.
 
- Compare one exact corner crossing with a near miss: only the crossing reports a contact.
 
- Keep a ball inside a sensor for many ticks: it scores once; exiting and re-entering after cooldown permits another
 score.
- Hit one bumper simultaneously with two balls: two masks appear four clocks apart, with independent arming bits.
 
- Pause after accepting a batch: that batch finishes once; later ticks cause no movement.
 
- Prepare during the second calculation: no staged position, contact or drain leaks into the next round.
 
- Drain one ball: the other continues. Drain the last: exactly one round-drain pulse follows the final contacts.
 
tb_physics.sv, tb_collision.sv, tb_multiball.sv and tb_two_ball_game.sv cover these kinds of contracts. The
additional archived geometry oracle under build/final_physics_audit/ compares swept cases against an independent
mathematical model. This is more informative than checking that a simulation simply runs: state the numerical result,
event count and latency that correct hardware must produce.

18. Procedural drawing and layer priority
This project mostly draws mathematically rather than reading a full-screen bitmap. A rectangle needs bounds
comparisons. A diamond can use abs(x-cx)+abs(y-cy)<=radius. A circle uses squared distance, with carefully limited
operand widths. Rails use constant coordinates or line equations; flippers use signed distance from a short line segment.
Lighting and outlines are extra tests near each shape's edge.
The following is a simplified teaching example, not a replacement module:
always @* begin
    pixel = BACKGROUND;                   // Every path has a default.
    if (inside_table) pixel = TABLE_COLOR;
    if (inside_trail) pixel = TRAIL_COLOR;
    if (inside_bumper) pixel = BUMPER_COLOR;
    if (inside_ball) pixel = BALL_COLOR;   // Latest assignment wins.
end
Blocking assignments express an ordered selection of the final colour. Several conditions may hold for the same pixel;
the last applicable assignment wins. This is the painter's-order rule. Synthesis builds priority logic from it, so layers affect
both visual correctness and timing.
The actual renderers draw subdued backgrounds and comic reactions before trails and table objects. Trails remain
beneath obstacles. Text, panels and pointers come later; live PLAY balls are drawn last, above notifications, sparks
and the pointer. READY, PAUSE and OVER have their own overlay treatment, so do not generalize the PLAY rule to
every state.
Trail samples are painted from index 7 down to 0. Index 0 is the newest. An older dim square must not overwrite a
brighter fresh square where they overlap. This is a useful example of a visual bug that can exist even when every
coordinate and colour individually looks correct.
Keep collision geometry and visible landmarks consistent. The bright ring around a bumper is an animation, not an
enlarged collision boundary. The circuit cat is decoration, not an obstacle. When adding a wall, change and verify its
intended collision representation as well as its picture; a drawn wall without a collision feels hollow, while a hidden
collision feels unfair.
19. Coordinates: logical playfield versus native VGA
Physics uses the compact table's coordinate system, with eight fractional bits. For example, a raw X position of 10816
represents 10816/256=42.25 logical pixels. The OLED shows the integer part, 42; VGA can show the fractional motion
more finely.
The native table fits inside a 768×512 region with origin (16,32). The conversion is:
native_x = 16 + floor(x_fp / 32)
native_y = 32 + floor(y_fp / 32)
Dividing Q8 coordinates by 32 is equivalent to multiplying the logical position by eight and discarding only fractions
smaller than one native pixel. In RTL, slices such as ball_x_fp[14:5] implement that conversion by wiring. For
(42.25,35.5), raw positions are (10816,9088), OLED centre is (42,35), and VGA centre is (354,316). One VGA pixel
represents one-eighth of a logical pixel. Five low Q8 bits are discarded; three fractional bits beyond the logical integer
position remain useful.
The VGA renderer receives the full native coordinate, not the OLED colour expanded into an 8×8 square. Its first ball is
a radius-eight circle with highlights, its second ball uses a chamfered silhouette to limit additional arithmetic, and its
bumpers have circular faces and smooth rings. Native text and menus have their own placement and scale.
Consequently the large screen gains detail and finer motion, while the OLED remains legible at its physical resolution.
The legacy logical x/y outputs of pinball_vga still exist, but Top leaves them unconnected. pixel_x and pixel_y drive
pinball_vga_scene. Connecting the legacy outputs instead would throw away the native rendering advantage.

20. Colours and small font memories
Both renderers return RGB565: red in bits [15:11], green in [10:5], and blue in [4:0]. There are 5, 6 and 5 bits per
component. Full red is 16'hF800, full green is 16'h07E0, and white is 16'hFFFF. A protected ball's principal bright blue
shade, 16'h05BF, has red 0, green 45/63 and blue 31/31, giving a cyan-blue rather than a dark pure blue.
The OLED consumes all 16 bits. Basys 3 VGA has four output bits per channel, so pinball_vga selects:
red   <= visible ? pixel[15:12] : 0;
green <= visible ? pixel[10:7]  : 0;
blue  <= visible ? pixel[4:1]   : 0;
These are the most significant four bits of each channel; they are not three adjacent four-bit slices of the 16-bit word.
Misreading this packing causes wrong colours. In the blue example the VGA outputs are (0,11,15).
The font functions are small constant lookup tables: a character code selects a 15-bit OLED glyph or a 35-bit VGA glyph.
Calling them ROMs describes their behaviour, not a guarantee of block-RAM inference. With small constant tables,
Vivado may implement them in LUT logic.
For the OLED, A is 010_101_111_101_101: five rows, each three bits wide. After selecting a message's character and its
local glyph coordinate (gx,gy), bit 14-(gy*3)-gx determines whether to draw ink. Native VGA similarly uses
34-(gy*5)-gx. Blank glyph cells leave the previously drawn colour visible. Character spacing prevents adjacent glyphs
from touching.
Scale comes from coordinate shifts. A doubled character divides local coordinates by two; a fourfold character divides by
four. These operations repeat glyph pixels without storing additional fonts. Each renderer selects one text region and
passes it through a shared decoder, avoiding a separate font circuit for every label. The code's signed arithmetic, explicit
widths and range guards remain important: subtraction and glyph indexing must not wrap outside the selected region.
21. OLED scan and the supplied SPI driver
The OLED driver's linear pixel_index runs through 6144 positions. Top computes oled_x=pixel_index%96 and
oled_y=pixel_index/96. Index 0 means (0,0), 95 means (95,0), 96 means (0,1), and 6143 means (95,63). These are
constant division and remainder operations that synthesis must implement; they are not software library calls.
Top derives the OLED clock by buffering bit 3 of a four-bit divider, giving 100 MHz/16=6.25 MHz. The protected controller
initializes the display, sets its column/row address range and serializes each RGB565 word in 16 clock cycles. Its frame
divider targets approximately 60 frames per second. The pixel payload alone occupies 6144×16/6.25 MHz≈15.729 ms;
initialization and frame commands are separate from that payload.
Read the actual edges carefully: Oled_Display updates its state, counters and SPI shift register on the falling edge of its
clk. While busy, sclk follows that clock; the falling-edge update prepares data for the next rising SPI edge. Top captures
oled_scene on the rising edge when oled_frame is asserted. This gives the renderer time to settle before the driver
takes the next pixel word on a falling edge. Describing both modules as rising-edge consumers would hide an important
half-cycle timing relationship.
frame_begin identifies a frame boundary; sample_pixel identifies pixel sampling opportunities; sending_pixels indicates
the streaming phase. Top uses frame_begin for scene capture and supplies combinational pixel_data continuously. It
does not need a framebuffer or to alter the supplied controller. The JC wiring is defined by Top and the constraints;
JC[2] is tied low because that OLEDrgb pin is unconnected.

24. Effects that consume little state
pinball_effects stores eight trail samples and two alternating banks of four sparks. Its two-bit phase divides the
approximately 240 Hz physics enable by four: trails are sampled at approximately 60 Hz. New positions enter index 0;
older samples shift toward index 7. Valid bits prevent uninitialized history from appearing. Renderers assign three
brightness bands by sample age; these are discrete fades, not alpha blending.
In two-ball play, the shared trail follows the white ball while it survives, then the gold survivor. trail_reset clears old
white-ball history on that handoff, and Top masks stale validity in the first outgoing scene. Otherwise an apparent line
could connect two unrelated ball paths. Two balls do not each have a separate eight-sample trail.
An accepted impact supplies the corrected hitting ball's position. Four sparks replace the oldest alternating bank,
allowing two closely spaced impacts to retain separate origins. Spark positions and velocities use fixed-point storage;
movement occurs at physics ticks. A four-bit lifetime decreases at the slower phase, starting at 15, for roughly a
quarter-second maximum burst. Out-of-screen sparks expire. Active motion freezes when paused, although an already
accepted impact may finish and create a frozen burst. The OLED uses compact rings and flashes; detailed spark
particles are sent to VGA.
Protection colour comes from the snapshot's save_timer!=0, shared by both balls and the trail. The OLED shows ceiling
seconds as S1..S6; VGA shows SAFE with seconds. On expiry, normal white/gold palettes return. Renderers describe
protection; the game module decides whether a drain consumes a life.
Original circuit-cat masks react to events 1/3/5/7 (major rewards), 6 (nudge) and 4 (save). They appear only while
feature_timer>120, the first approximately half-second of a 240-tick notification. PLAY permits these reactions; READY
permits the saved reaction and moves it below the charge area. Repeated combo event 2 is excluded to prevent
constant interruption. OLED expresses the reaction with tiny faces, sweat or stars; VGA adds "YATTA!", "NANI!" or
"PHEW!". The latest notification can replace an earlier one. It is not an event queue.
The pointer uses the same logical mouse coordinates and hover rectangles as Top's click logic. VGA transforms the
pointer to the native origin/scale; OLED draws a compact cross. A hidden or disabled pointer must not highlight a button.
Visible boundaries and accepted clicks should be tested together.
25. Build your own display system in manageable steps
Start with fixed colour bars and a grid. Verify RGB packing, corner coordinates, OLED order and VGA timing before
connecting game state. Next draw one stationary shape, then drive it with a clocked coordinate. Add a frame snapshot
and deliberately change the producer halfway through a frame to verify that the current picture stays stable. Add integer
OLED motion first, then fractional native motion, HUD text, and finally effects.
For verification, check pixels at shape centres, edges and just outside bounds; inspect full-frame captures for every
state. Test overlapping old/new trails, protected and unprotected balls, drained visibility, both balls over a notification,
pointer corners and modal overlays. tb_renderer, tb_vga_renderer, tb_vga, tb_vga_clock, tb_effects and tb_top
cover these different responsibilities. Test bundle packing with nondefault fractional values: all-zero values cannot reveal
swapped fields.
Finally, rerun implementation timing. A small extra comparison late in a pixel selector can extend a priority chain enough
to miss the 25 ns VGA period. Shared arithmetic, bounded widths, constant masks and late colour gates help control
cost. Correct simulation proves behaviour; successful routed timing proves the implemented circuit can meet its
specified clocks. Both are required for a dependable EE2026 display design.

active pixel and porch in simulation. The physical pass condition is a stable picture at the intended mode through the

29. Vivado flow, constraints and resource reasoning
FDP2026.xpr is the saved project. The part and top module must match the board. A module existing on disk does not
necessarily mean it is registered in the project's source set. scripts/verify_project.py checks registration, part
selection, JC mapping, explicit-net guards and protected-driver hashes. scripts/verify_vivado_project.tcl checks
the saved Vivado project settings and compile order.
scripts/build.tcl provides a repeatable batch flow. It reads the mixed VHDL and Verilog sources, reads board
constraints, synthesizes the top, reads the implementation-only collision timing constraints after registers are mapped,
then optimizes, places, physically optimizes, routes, reports and writes the programming file. It stops if worst setup or
hold slack is negative. The board pin check also rejects a stale JA design when this project expects JC.
Understand three different questions. Elaboration asks whether modules, parameters and ports form a legal design.
Simulation asks whether the model's behavior matches the expected contract. Synthesis/implementation ask which
physical resources implement it and whether signals meet timing after routing. A syntax-correct program can fail any
later question.
Setup, hold and why constraints are not a speed-control trick
Setup requires data to arrive before its receiving edge; hold requires it to remain stable around the edge. Worst negative
slack means at least one checked path misses its requirement. At 100 MHz, an ordinary single-cycle path has a 10 ns
clock period; the native pixel circuit operates against a 25 ns pixel period. Clock uncertainty, skew, setup requirements
and routing are included in the actual analysis, so a period is not all available logic time.
Board pins and generated clocks are in Basys3_Master.xdc. Asynchronous buttons/switches are exempted only into their
first synchronizer stage. Related display clocks remain timed. The scene crossings must settle in the actual edge
relationship, which can have only a 5 ns setup window. Putting producer registers before the crossing shortens it by
removing derived graphics logic from that path.
The collision block's 16-cycle setup / 15-cycle hold exceptions apply to stable snapshot-to-result paths. They are justified
by the scheduler's delayed capture, not by a desire to silence failures. The ordinary selector, control and queued-event
paths must still meet normal timing. Changing the capture schedule requires reviewing those exceptions. For the general
command semantics, see AMD's UG903 multicycle-path syntax; the project's exact scoped queries are in its XDC file.
Why source-code length is not resource cost
A multiplication can infer a DSP or a substantial LUT circuit. A constant shift may be mostly wiring. A combinational for
loop normally unrolls into replicated hardware; it is not an economical CPU loop that takes one instruction per iteration.
Conversely, a sequential controller with operand multiplexers can reuse one expensive circuit at different times, as the
two-ball scheduler does.

32. Extending a finalized design without breaking its contracts
Before adding an object, define its logical geometry, its visual geometry, its contact bit or event type, its reward, its
arming/exit envelope and any collection memory. Then update collision, physics filtering, rules, renderers and tests
coherently. The present 14-bit masks have no spare bit. Expanding them changes arrays, interface widths, bundle
widths and test fixtures; stealing a bit from another object silently changes gameplay.
Before changing ball count, estimate state storage and arithmetic separately. A third set of coordinates is cheap
compared with a third collision circuit. A shared engine needs another scheduling slot and longer whole-world latency,
while pending event/drain spacing and constraint endpoints must remain correct. The current two-ball design does not
automatically generalize merely by changing a constant.
Before increasing resolution, derive a supported pixel clock and complete timing mode. Pixel rate determines the budget
for computing each output pixel. A 65 MHz mode has a shorter combinational period than 40 MHz even if object
geometry is unchanged. Increasing coordinates can also widen multipliers. A display resolution change therefore
includes timing, arithmetic widths, layout, constraints and physical converter testing.
Before adding a graphic, determine its final layer and state visibility. A reward popup should not hide a ball or button. A
repeated combo notification should not refresh a distracting animation indefinitely. Reuse existing timers and masks
when appropriate, but make the behavior intentional rather than dependent on an unrelated field changing by chance.

34. Glossary and source references
Term
Meaning in this guide
RTL
Register-transfer-level description of state and logic between registers
Combinational
Output depends on current inputs; no intended memory
Sequential
Registers retain state across clock edges
FSM
Stored operating state plus transition/output decisions
Datapath
Arithmetic, comparisons, multiplexers and registers operating on values
Clock enable
Condition deciding whether state updates on an existing clock edge
Q8
This project's signed fixed-point values with eight fractional bits; divide by 256
BCD
Four bits per decimal digit; valid digit values 0 through 9
Snapshot
Captured values held as one calculation or display transaction
Atomic commit
Related results become visible together at one clock edge
Hysteresis
Different entry and exit thresholds prevent repeated toggling/contacts
Metastability
A register can take longer to resolve after an asynchronous edge near sampling
LUT
Configurable Boolean lookup logic resource
DSP
Dedicated arithmetic resource in the FPGA
BRAM
Dedicated block memory resource
MMCM / BUFG
Clock synthesis/management primitive and global clock buffer
Setup / hold slack
Margin relative to required data arrival/stability timing
SPI
Serial data interface used to send commands and pixels to the OLED
RGB565 / RGB444
Packed color formats with 5/6/5 and 4/4/4 component bits
